# Solvency Observatory

A standalone TypeScript website for Publicly Verifiable Solvency System. Based on
main commit `e798b86c253cb9b4f84991d963b21a558ea087ca` (Poseidon2, eight leaves,
Noir/Honk verification). All frontend source and its independent lockfile live
in `website/`; root contract/prover dependencies are unchanged.

## Run locally

From the repository root:

```sh
cd website
npm ci
npm run dev
```

Open the local address printed by the command. `npm run build` creates `dist/`,
which can be served by any static web server. The development command watches
TypeScript/CSS; restart it after editing the HTML or public assets.

```sh
npm test
npm run typecheck
npm run build
```

## Use

The default screen explicitly uses demonstration data. Its ledger and Poseidon2
root match main's fixtures (49,550 wei liabilities). The 60,000 wei reserve amount
is illustrative, not a queried or attested company balance.

1. Enter a browser-accessible RPC, expected chain ID and independently verified
   SolvencyRegistry address. The portal is read-only; no wallet/private key is needed.
2. All reads are pinned to one block. The portal reads currentEpoch, totalReserves,
   epochCount, verifier and contract code. Current reserves are clearly distinguished
   from the liabilities recorded at the epoch timestamp.
3. In Your balance, select the custodian's `proof-username.json` generated by main.
   Enter the expected ID and balance in **wei** from your own records.
4. The browser validates the file, reconstructs the Poseidon2 Merkle-sum path,
   and checks both root and total against the selected snapshot.

Try the example customer to explore the complete flow without an RPC. Choosing
it explicitly switches to demonstration mode. Live connection errors never fall
back to a successful demo check.

## Scope and privacy

- Supports main's three-level, eight-leaf Poseidon2 proof format. The older Keccak
  and split-balance branches are intentionally not presented as compatible.
- Proofs and expected account details stay in browser memory, not localStorage.
  They are never sent in RPC requests. No analytics, third-party fonts, server-side
  uploads, wallet signing or custodial keys are used.
- RPC requests expose the selected contract and the visitor's network metadata to
  their RPC provider. Use a CORS-enabled endpoint. HTTPS-hosted pages may be blocked
  from accessing a local HTTP node by browser private-network/mixed-content policy;
  use the local website for an Anvil demo, or an HTTPS endpoint for hosted use.
- Never put privileged RPC/API secrets into a public frontend. This app does not
  provide an RPC proxy or store connection settings.
- The portal does not authenticate arbitrary contracts or RPC providers. A contract
  can imitate the ABI. Confirm the deployed address, implementation and network
  independently. Reading a verifier address is not a code audit.
- Successful inclusion is not proof of complete liabilities, ownership/eligibility
  of reserves, locked assets, or future withdrawal availability. The last liability
  snapshot and reserves at the read block may describe different times.
- Main's inclusion proofs can reveal sibling subtree sums. The circuit proof and
  an individual customer inclusion proof are distinct checks.

## Design

A Basel research observatory: the presentation's turquoise, dark evergreen ink,
serif numeric typography, ruled ledger sections, and a named team page. No generic
hero/feature-card landing page. Layouts adapt to small screens; controls have
labels, keyboard focus and live status messages, with reduced-motion support.

## Validation

Seven tests cover parity with main's fixture, identity/amount mismatch, altered
paths, root/total mismatch, malformed/range-invalid data, RPC input rejection and
pinned-block RPC reads. Type checking and a production build pass. No live deployed
registry was supplied; live behavior was checked with mocked RPC responses, not a
real blockchain connection. Browser/visual testing was not performed.
